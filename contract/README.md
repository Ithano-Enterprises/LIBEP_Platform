## Executable examples

`fixtures/mobile-v0.2-batch.json` contains all four record kinds, an unmatched
species, a correction clearing a note, an incorrect device clock, and a return
headcount different from departure. IDs, timestamps and values are synthetic
**TEST ONLY** data, not real reference rows or deployment seeds. Never send them
to a hosted project. A matching test device/reference setup does not yet exist.

The Deno tests import the same JSON without filesystem/network permissions.
Mobile developers can load it directly as JSON; do not import server modules.
To check an actual mobile checkout with Node 24:

```sh
node scripts/check-logbook-contract.mjs /path/to/apps/logbook/src/data/sync/payload.ts
```

This calls that checkout's real `buildBatch`, starting in reverse dependency
order, and compares its complete output with the fixture. It does not test
SQLite, networking, authentication or persistence. Repeat when mobile payloads
change; this check is not automatically run against external PR branches in CI.

## Candidate validation

`supabase/functions/_shared/logbook_contract.ts` validates unknown JSON:

- envelope version 1; four explicit record kinds; UUIDv4 ledger IDs;
- required fields, including explicit nulls; unknown fields rejected;
- original local-name text and timestamp retained unchanged;
- positive whole-kg decimal strings for catches/corrections; nonnegative
  whole-kg total for close, including zero-catch trips;
- one trip UUID (`trip_start.trip_id = id`), positive departure crew and
  nonnegative return crew; unequal crew is not rejected;
- paired latitude/longitude, valid ranges and nonnegative accuracy/distance;
- full replacement correction fields, including nullable species/hold/note;
- RFC 3339 timestamps with a timezone and valid calendar dates. Leap-second
  spelling is not supported by this candidate or generated by the current app;
- malformed envelopes return 400, oversized record arrays 413, invalid records
  422 with a safe known field name and valid record ID when available.

Numeric strings are never converted through JavaScript Number. Input is not
rounded, trimmed, rewritten, reordered, deduplicated or persisted. Syntactically
valid old timestamps are accepted, not corrected. Duplicate-ID content comparison,
reference existence, trip membership, total recomputation and correction-chain
concurrency belong to the future transaction layer, not this validator.

Callers must supply `maxRecords` and `maxCrew` (null means no crew ceiling at
shape level). Tests use 50 rows, matching the app's present batch builder; this
is not an approved server limit. No runtime deployment configuration is added.
The minimum headcounts come from current mobile behaviour; the maximum of 24
remains provisional. `device_id` in input is only syntax-checked: it must never
be trusted as authenticated identity.
